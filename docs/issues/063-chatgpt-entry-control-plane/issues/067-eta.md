Parent: #63
Related: #65 (start_development_task, the primary consumer of this estimate)

## Objective
Give `start_development_task` (and, additively, `submit_codex_task`) a duration estimate at submission time that is honest about its own confidence, rather than either omitting an ETA entirely or fabricating one.

Note: if #65 lands first, its acceptance criteria already require this estimate and this issue's implementation may be absorbed there. Filed separately because the estimator is independently useful (e.g. from `get_task_status` for a running task's remaining time) and independently testable.

## Scope
- `gateway/app/services/store.py`: `estimate_task_duration_seconds(session, *, project_id, mode, engine)`.
- Consumed by `start_development_task` (#65) and additively exposed on `get_task_status`/`list_recent_tasks`.

## Requirements
- Sample: tasks with `state == 'completed'`, `started_at is not null`, `completed_at is not null`, `created_at > now() - 90 days`, matching `project_id + mode + engine`, ordered by `completed_at desc`, limited to 50.
- Compute the **median** of `completed_at - started_at`, read directly from those two columns (not parsed out of `result_json`) — a single long-timeout outlier should not dominate the estimate the way it would dominate a mean.
- Fewer than 5 matching samples widens the query, in order: drop `engine`, then drop `project_id`, then drop `mode` (global median across everything). Report which level was actually used as `eta_basis` (`"project+mode+engine"` / `"project+mode"` / `"mode"` / `"global"` / `"none"`) and how many samples backed it as `eta_sample_size`.
- **Zero samples at every level returns `eta_seconds: null` and `eta_basis: "none"` — never a fabricated number.** An estimate that cannot say what evidence it rests on is exactly the failure council finding **F29** identifies in #54's cost-accounting acceptance criteria ("best available evidence" is unfalsifiable without a stated basis); this issue's estimator must not repeat that mistake for ETA.
- If the target executor is at or over its concurrency limit, add the median remaining wall time of its currently `RUNNING` tasks and report it as a separate `queue_wait_seconds` field rather than folding it silently into `eta_seconds`.

## ARO
- **F29**: directly addressed by the null-when-unknown rule and the explicit basis/sample-size reporting. Any future change to this estimator that removes the `eta_basis`/`eta_sample_size` fields, or that returns a number without them, reintroduces the failure this issue exists to avoid.
- Assumption: 90-day / 50-sample / 5-sample-minimum are reasonable starting constants for this deployment's current task volume; revisit if task volume changes by an order of magnitude.

## Test plan
- New unit tests in `tests/unit/test_store.py` (or extending `tests/integration/test_store_and_mcp.py`): correct median computation with a synthetic sample set including an outlier; correct fallback ordering (engine → project → mode → global) as sample count is varied; `eta_seconds: null` / `eta_basis: "none"` at zero samples; `queue_wait_seconds` present only when the executor is saturated.

## Definition of Done
- No code path in this estimator can return a number when zero historical samples exist at any level.
- `eta_basis` and `eta_sample_size` are present on every non-null estimate.
