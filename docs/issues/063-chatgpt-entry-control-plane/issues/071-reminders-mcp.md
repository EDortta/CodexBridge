## Objective
Let an operator say "remind me of Z" in ChatGPT and have it become a real Google Calendar event on the operator's own calendar, with a popup notification on their phone — without CodexBridge running a scheduler, since it does not have one and a Raspberry Pi is not where to add one (council finding **F12**). The calendar itself is the scheduler.

## Scope
- New `gateway/app/services/google_calendar.py` (async, `httpx.AsyncClient`-based; the `httpx.AsyncClient` and the RS256 signer are both dependency-injected so the module is testable without any network access).
- Two new MCP tools: `create_reminder`, `cancel_reminder`. **Deliberately no `list_reminders` in v1** — the operator already has a full-featured client for browsing and deleting reminders (the Google Calendar app, on the same phone that receives the popup), and a listing tool would drag in a query contract, pagination, a new read scope, and — since this ships with one shared calendar — a cross-user read of somebody else's reminders.
- New OAuth scope `codexbridge.reminders.write`, added to `gateway/app/core/config.py`'s `oauth_default_scopes` and to the operator's grant in `users.json`.

## Requirements — why the tool takes a computed datetime, not free text
`python-dateutil` is already a dependency but is **not** a natural-language parser — `dateutil.parser` raises on `"sexta que vem às 15h"`. ChatGPT already holds the operator's timezone, the current instant, and the full utterance including "próxima" vs. "esta". So: `when` is ISO 8601 **with a UTC offset**, computed by ChatGPT itself. A naive (offset-less) datetime is rejected rather than silently assumed into a timezone. `dateutil.parser.isoparse` is used (not `datetime.fromisoformat`, which on Python 3.10 rejects a trailing `Z`). The server **echoes the resolved local time back** in the tool's text response so ChatGPT reads it aloud and the operator catches an arithmetic error before the reminder matters — `when &lt;= now + 30s` → typed `reminder_in_the_past`, echoing both the parsed instant and the server's own `now`; `when &gt; now + 2 years` → `reminder_too_far_out`.

## Requirements — idempotency without a new table
`/mcp` sits outside this gateway's `Idempotency-Key` HTTP middleware (`gateway/app/api/scope.py` excludes it deliberately), so idempotency is reconstructed inside the tool itself: an optional `idempotency_key` argument is folded, together with the operator's user id, into a **deterministic Calendar event id** (`sha256` digest, base32hex-encoded — exactly Google's allowed event-id alphabet, 26–28 chars, within the 5–1024 bound). `events.insert` with an id that already exists returns 409; the handler then does `events.get` on that id and returns the existing event with `created:false` (and, if that event was since cancelled by the operator, says so rather than silently resurrecting it or claiming success). This is durable across gateway restarts and needs no schema change.

## Requirements — event shape (each choice is load-bearing)
- `transparency: "transparent"` — a reminder must never mark the operator as busy or consume a free/busy slot; this is the single most common mistake with this pattern.
- 15-minute duration, not zero-length — several calendar clients render a zero-duration timed event inconsistently.
- `reminders: {useDefault: false, overrides: [{method: "popup", minutes: <lead_minutes>}]}`. **`method: "email"` is deliberately omitted** — a Calendar reminder email goes to the *authenticated user*, which here is the service account, so it would be mail sent to nobody useful.
- **No `attendees` array, ever.** A service account without Domain-Wide Delegation gets `403 forbiddenForServiceAccounts` when adding an attendee. The reminder must reach the operator by calendar *membership*, not by invitation.
- `extendedProperties.private.source = "codexbridge"` (plus `requested_by`, `created_via`, `idempotency_key`) from day one, even though nothing reads it yet — it is what makes a future listing surface possible via `events.list?privateExtendedProperty=source%3Dcodexbridge` without a gateway-side table, and adding it later would not retroactively tag events already created.

## Requirements — service-account signing and the sharing caveat
The service-account JWT is RS256; this project's virtualenv has neither `cryptography` nor `pyjwt`, and the reference implementation elsewhere in this operator's environment (`job-outreach/src/outreach/calendar_client.py`) signs by shelling out to `/usr/bin/openssl`, which is present on the gateway host. This issue follows that precedent rather than adding a cryptography dependency — but **ports it to async** (`asyncio.create_subprocess_exec` for the signer, `httpx.AsyncClient` for the two HTTPS round trips), since the reference implementation is synchronous `urllib`/`subprocess.run` and a straight copy would stall the gateway's event loop for the duration of two round trips from a Raspberry Pi. An in-process access-token cache (memory only, ~55-minute TTL) keeps the steady state to one round trip per call; a hard `httpx` timeout (10s connect / 20s total) prevents a Google outage from pinning a worker.

A service account can only write to a calendar **explicitly shared with its `client_email`** — there is no way around this without Domain-Wide Delegation. The operator must, once: create a secondary calendar (recommended name "CodexBridge") owned by their own account, share it with the service account's `client_email` using "Make changes to events" (not "See all event details," which is read-only and produces a 403 that reads like a 404 to a careless caller), and put that calendar's id in `CODEX_BRIDGE_GOOGLE_CALENDAR_ID`. Every 403/404 the calendar API returns must be translated into a message that **names the `client_email` and the exact sharing step** — the `client_email` is not a secret and is what makes the message actionable; the `private_key` must never appear in any format string anywhere in this module. A `400 invalid_grant` token-exchange failure should mention checking the host's clock (`timedatectl`) — an out-of-sync Raspberry Pi is a real, previously-seen failure mode for JWT-bearer flows.

**Stated honestly, not hidden:** Google documents event `reminders` as being for "the authenticated user" — which here is the service account, not the operator. Whether a popup override written by the service account actually fires on the operator's own device cannot be verified from source alone. Mitigation: also have the operator set the shared calendar's own default notification setting, and make **"the phone actually buzzed"** an explicit, named acceptance criterion of the live smoke test — not an assumption. If the override turns out not to carry through, the fallback is `reminders: {useDefault: true}` with `lead_minutes` dropped from the tool schema, and this issue's code must be adjusted accordingly rather than shipping a claim that was never observed to be true.

## ARO
- Credential custody: the service-account key file is installed at `/etc/codex-bridge/google-calendar-sa.json` (or similar), referenced by path, never embedded — following `.docs/agents/credentials-operations.md`. Recommend provisioning a **new, dedicated** service account rather than reusing `blog-agenda@igreja-pequena-agenda.iam.gserviceaccount.com` (already used by two unrelated projects) so that revoking it does not break them.
- New egress dependency: this is the first time the gateway host dials *out* to a third party (`oauth2.googleapis.com`, `www.googleapis.com`) from inside a request handler, rather than only accepting inbound connections. Must be recorded in `docs/threat-model.md` and `docs/security.md`.
- Multi-user is out of scope for v1 and deliberately not built, but named now: one gateway-wide calendar means every operator's reminder is visible to every other operator if a listing tool is ever added. The natural home for a per-user `calendar_id` is beside `scopes` in `users.json`; `extendedProperties.private.requested_by` is populated from day one specifically so that migration is a filter, not a backfill.

## Test plan (without touching Google)
- New `tests/unit/test_google_calendar.py`: JWT assembly with a fake signer (assert `iss`, `scope`, `aud`, `exp - iat`); deterministic event-id derivation (same seed → same id, different user → different id, alphabet subset of Google's allowed set, length in bounds); exact event body for a fixed input (including the explicit absence of an `attendees` key in every case); datetime validation (naive input, past, too-far-out, trailing-`Z`); error mapping via `httpx.MockTransport` for 404/403/400-`invalid_grant`, asserting each message contains the `client_email` and the sharing instruction, and asserting **no fixture's `private_key` value ever appears in any produced message** (a real assertion, not a comment). One `openssl`-signing round-trip test, skipped if the binary is absent.
- New `tests/integration/test_mcp_reminders.py`: `tools/list` includes both tools; a principal missing `codexbridge.reminders.write` gets 403; happy-path create against a fake calendar client; a repeated call with the same `idempotency_key` returns `created:false` with the same id; **an unconfigured gateway still answers `submit_codex_task` normally**, proving this feature is not load-bearing for the rest of the system.
- Live smoke test (post-deploy, against the operator's real calendar): create a reminder a few minutes out, confirm the phone actually notifies, cancel it, confirm the gateway's own logs contain zero occurrences of "PRIVATE KEY".

## Definition of Done
- A reminder created from ChatGPT appears on the shared "CodexBridge" calendar and the operator's phone visibly notifies at the scheduled time (verified live, not assumed).
- A repeated identical request never creates a second event.
- No response, log line, or error message from this module ever contains the service account's private key.
