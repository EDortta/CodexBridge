CodexBridge

A governed bridge between a conversation and a repository it is not allowed to break.

The agent goes to the code.
The code goes nowhere.

I wanted to say “go resolve issue #68 in that project” to a chat window and have it happen on the machine that actually holds the repository. Every easy version of that is a bad idea: a public SSH port, an executor that accepts arbitrary filesystem paths, one token that reaches everything.

So the interesting part of CodexBridge was never the execution. It was the refusals. This page is the notebook: what runs today, what is still in pencil, and where it is heading.

The sketch

One rule holds the whole design up: the gateway never dials the executor.

frida and devel3 are just the names of my two machines: one exposed to the internet, one that holds the code.

ChatGPT talks only to the gateway, and only about project_id. It cannot name a directory, so it cannot ask for one it was never given. The executor opens a reverse wss connection outward and waits; work comes back down that same socket. Then the executor resolves the real path and checks it against its own allowlist before codex exec runs — a second gate, on a second host, that the first one cannot talk its way past.

Intent is classified before it runs: read, controlled_write, or sensitive. Anything that smells like deploy, migration, push or rm -rf is promoted to sensitive and stops for a human.

Two gates, not one. Learning that they were two — and that closing only the near one felt like finishing — cost me a week. Page 7.

“Why not just use the cloud?”

Because a cloud agent needs your code to come to it. This one goes to where your code already is.

Every cloud coding agent has the same shape: you hand it a hosted repository, it clones into a sandbox of its own, it hands you back a pull request. The shape works. It charges three things.

  1. The code has to be reachable by them, and it is copied to them. Pushed to a host they can see, an app authorized, the work running on someone else's machine.
  2. The agent only ever sees the repository. Not the staging database, not the VPN, not the licensed toolchain, not the branch you never pushed.
  3. You get their agent and their model, and that choice changes underneath you.

CodexBridge inverts the first one. The other two fall out of it.

What this reaches

The machine where the code already sits — with its database, its VPN, its licensed toolchain, its half-finished branch. The agent arrives; the code stays put.

And the folder in ~/Projects/something that you never pushed anywhere. No cloud agent can touch that one. It is not a policy question: that folder does not exist for them.

What the cloud does better

Nothing to keep alive. No host of yours, no executor to restart, no machine that has to be awake at 3am.

Elastic compute. Ten agents at once without anything of yours getting hot.

And this shape is not exclusive. A self-hosted runner is the same idea behind a checkbox. The difference is that here it is the whole product, with the refusals built into the path — not a setting.

They are not competing. I run both.

In my own use, two tools sit in one conversation. ChatGPT's GitHub connector does the planning, where the code is hosted. CodexBridge does the execution, where the code actually lives. Neither had to absorb the other, and I never had to choose.

The folder decides. Bound to a forge, with the credential on that machine, and the issues live in the forge. Not bound, and they live in CodexBridge. Same sentence from the chat either way — that second half is designed and written down, not built: #78, #79, #80.

Four repositories, one habit

The bridge is the visible one. The other three are why I trust it enough to leave it running.

the bridge

CodexBridge

FastAPI gateway plus a reverse-channel executor. Persistent task queue that survives a restart, incremental logs, cancellation, git diff of what the agent actually changed.

the pocket

CodexBridgeMobile

Android client. Deliberately not a mobile IDE: it exists so the human decision — approve, stop, re-read, unblock — does not have to wait until I am back at a desk.

Flutter · 126 Dart files · built against a versioned contract

the contract

AI-Agents

The rules every agent reads before touching a repository: a global AGENTS.md, role guides, a hard docs/limits.md, an issue workflow. Installed by script, upgraded by script, never hand-copied between projects.

Portable across Codex · Claude · Copilot · Cursor · Gemini

the enforcement

AI-GovernanceKit

The same contract, made executable: doctor checks, session resume, start-work, validation, session-close, and context budgets that fail loudly instead of silently truncating a contract.

CLI · MCP server · CI hooks · audit evidence

Written down like that it sounds tidy. It is not: the kit exists because I kept re-explaining the same boundaries to a fresh agent every morning, and losing the argument in different ways each time. Governance here is not paperwork — it is the memory the agent does not have.

Same four files land in every project: AGENTS.md, software-overview.md, limits.md, project-rules.md. Only the last one is mine to edit.

What runs, and what is still in pencil

A demo hides this column. A notebook cannot.

Runs today

  • MCP endpoint over HTTPS with 14 tools — submit, follow, read logs, cancel, approve, resume a session.
  • Reverse wss channel: the executor dials out, the gateway never dials in.
  • Durable queue that recovers its work after a gateway restart.
  • Project allowlist on both sides, gateway and executor, checked against a resolved realpath.
  • Policy levels with keyword promotion — sensitive intent stops and waits for a person.
  • Explicit sandbox on every dispatch: read-only unless the task was already classified as a write.
  • 670 tests across 47 files, and every fix ships with a test that fails without it.
  • A conversational entry point: “resolve issue X of project Y”, from the chat, end to end.

Still in pencil

  • PostgreSQL in production. Everything proven so far was proven on SQLite.
  • Missions over HTTP — the chat can start work, the REST surface for it is specified and not built (#68, #69).
  • A second runner. Claude Code beside Codex, behind one provider interface (#64).
  • The mobile client against a live gateway. Today it is wired to the contract artifact, not to a deployed host.
  • One adversarial-review finding is still open and marked ship-blocking. It is written into docs/security.md and it is not merged. It is not fixed by being unmentioned.
  • Planning from the chat. Epics and issues live in the gateway and reach the mobile client, but no MCP tool writes them, so “open an epic for X” has no handler yet (#78). Letting a folder bound to a forge keep its issues there instead is designed and not built (#79, #80).
  • Nothing here deploys itself. That one is not a gap — an agent pushed to production once, unasked, and deploy has been a human gate ever since.

Where it is going

Each step exists because the previous one turned out to be too small.

  1. A contract before an API epic #1 — in flight

    A versioned, published contract the mobile client is built against, with a compatibility gate in CI. Five pull requests open; the contract versions collide on purpose so the merge order is a decision, not an accident.

  2. A conversational control plane epic #63 — building

    Talking is the interface. Name an issue and a project, get an estimate, get a delivery with branch, commit, files and diff stat — and an out-of-band notification when it is done, because nobody should have to watch a socket.

  3. A development orchestrator, not a runner epic #40 — specified, 18 issues

    Durable missions with a state machine, planning and review gates, worktree and branch management, scheduling for now / later / overnight, and per-provider cost accounting. This is where the crossed-out title on page 1 finally stops being true.

  4. A fleet, and how a project earns access to it epic #73 — open question

    Several nodes, several executors, and an adoption plane that decides how a new repository becomes reachable at all. The honest status: I know the shape and I do not yet know the authorization model.

How I actually work with agents

I use AI for most of the code in these repositories. That is the easy half. The half that took the work was learning where not to believe it.

  • Contract first The boundary is written and published before the code that has to respect it. An API the client guessed at is a bug with a schedule.
  • Adversarial councils Reviews run in two rounds through three lenses — security, skeptic, second-caller. Findings that survive get fixed; findings that survive and are not fixed get written down by name.
  • A failing test, first Every fix ships with the test that fails without it. Otherwise “fixed” is a claim about the past.
  • Napkin lessons A file of mistakes in full, including the ones the agents made against me and the ones I made against myself. It is the only artefact here that gets read more than once.
  • Session close Every stage ends the same way: handoff updated, lessons written, next step named. A session that ends silently costs the next one an hour.
  • Deploy is human No agent, in any of these repositories, deploys anything. Implementing an issue never includes shipping it.

docs/napkin-lessons.md — 2026-08-30

“When a request for automatic access to X crosses more than one process and host, each with its own decision point, fixing the one that is easiest to reach — usually the nearest — and stopping there gives the impression of a complete delivery without delivering the result that was asked for. Trace the whole path first, then say out loud which part is closed and which is not.”

That is one entry out of many, and it is the reason this page has a column called “still in pencil”. A tool that dispatches an AI agent into a repository is only worth building if the person running it is honest about what it cannot do yet.
